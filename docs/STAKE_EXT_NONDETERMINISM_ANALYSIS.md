# Недетерминированность верификатора stake-ext: анализ (часть E)

Документ к плану `hotfix/Oct-2026-0`, часть E. Это **анализ**, а не правка: вердикт
верификатора не меняется в текущем цикле. Цель — зафиксировать механизм,
инвентаризировать зависимость вердикта от локального состояния, показать, что
именно должно быть закрыто до правки, и определить порядок безопасного перехода.

Все ссылки на код — по `cellframe-sdk`, файл
`modules/service/stake-ext/dap_chain_net_srv_stake_ext.c`, если не указано иное.

## 1. Суть проблемы

Вердикт проверки разлока (`s_stake_ext_lock_callback_verificator`, :1147)
читается из **локального кэша** `s_stake_ext_cache`, а кэш наполняется
**асинхронно**. Отсюда: результат валидации зависит от того, успела ли очередь
событий обработать соответствующее событие к моменту проверки блока, а не только
от данных цепи.

Механизм:

| Шаг | Где | Что происходит |
|---|---|---|
| Чтение | :1188 | `s_find_stake_ext_by_hash_fast(s_stake_ext_cache, &l_stake_ext_hash)` — берётся элемент кэша |
| Вердикт | :1195 | `switch (l_stake_ext->status)` — вердикт определяется статусом из кэша |
| Вердикт | :1208, :1213-1214 | победители (`winners_cnt` / `winners_ids`) тоже из кэша |
| Вердикт | :1229, :1254 | `end_time` из кэша |
| Запись | :799 (`dap_stake_ext_cache_event_callback`) | единственный писатель кэша |
| Регистрация | :101 | `dap_ledger_event_notify_add(l_net->pub.ledger, dap_stake_ext_cache_event_callback, s_stake_ext_cache)` |

Ключевое: писатель вызывается через механизм уведомлений леджера и выполняется
**в другом потоке**, тогда как проверка блока идёт синхронно в потоке валидации.
Порядок «событие → кэш» и «блок → проверка» между собой не сериализован. Значит,
валидация может опередить оседание события `ENDED`/`CANCELLED`, и тогда разлок
будет проверен по устаревшему статусу (`ACTIVE` вместо `ENDED` или наоборот).

Латентность низкая: разлоки редки, поэтому на практике кэш обычно успевает
наполниться, и расхождение не проявляется. Но **гарантии нет** — это гонка, и она
зависит от скорости очереди, а не от цепи.

## 2. Инвентаризация: что именно читается из локального состояния

Три поля определяют вердикт; каждое дублируется данными цепи:

| Поле | Чтение | Откуда берётся в цепи |
|---|---|---|
| `status` | :1195 | события `STAKE_EXT_STARTED` / `ENDED` / `CANCELLED` |
| `winners_cnt`, `winners_ids` | :1208, :1213 | событие `ENDED` |
| `end_time` | :1229, :1254 | вычисляется: `s_stake_ext_calc_end_time()` (:679) из `start_time` и параметров `STARTED` |

Запись этих же полей в кэш: :267 (`end_time` при `STARTED`), :776-777
(`end_time`, `winners_cnt` при `ENDED`), :909 и :961 (`end_time` из события).

Вспомогательный факт: `ts_created` разлока уже берётся **из леджера** (:1226,
`l_lock_tx->header.ts_created`) — то есть один источник истины в верификаторе уже
используется, что подтверждает: переход на события не требует новых механизмов,
только перенос трёх оставшихся чтений.

## 3. Почему это отдельный релиз

Вердикт верификатора **ужесточается**: разлок, который сейчас проходит по
устаревшему `ACTIVE`, после перехода на события начнёт отвергаться (и наоборот —
разлок, отвергнутый из-за пустого кэша, начнёт проходить). Это изменение
результата валидации, то есть консенсусное изменение:

1. требует собственного декрета (номер из `dap_chain_policy.h`) — как все
   остальные правила этого цикла;
2. требует сравнительного replay-анализа **до** правки, чтобы измерить, сколько
   вердиктов изменится на реальной истории;
3. не может ехать в одном релизе с правками, которые уже запушены: смешение
   усложнило бы разбор любого расхождения.

## 4. Обязательные условия (prerequisites)

Правка вердикта без этих двух условий **не даст полного эффекта** — она закроет
гонку, но не пустое состояние:

- **Провал `s_no_datum_notify`.** При пересборке индекса уведомления подавлены
  (`dap_chain_cs_blocks.c:50`, установка :3037, снятие :3046, проверка :2270).
  События, прошедшие под этим флагом, до писателя кэша не доходят. Если после
  пересборки кэш пуст, верификатор ответит ошибкой «не найдено» независимо от
  того, читает он события или кэш.
- **Отсутствие персистентности stake-ext.** Секции снапшота у модуля нет вовсе
  (проверено: `dap_ledger_add_snapshot_section` в файле не вызывается). При
  no-scan старте кэш пуст по определению. Это тот же класс проблемы, что закрыт
  в части A для декретов: производное состояние, которое не попадает в снапшот и
  молча теряется при старте без скана.

Порядок работ: сначала персистентность (секция снапшота, по образцу
`decree_journal`) и закрытие подавления уведомлений, затем — переход вердикта на
события под декретом.

## 5. План анализа (E4): как измерить безопасность правки

До любой правки вердикта:

1. Построить клон цепи (по методике из `local-backbone-repro-setup`: `cp -c -R`,
   удалить `*.dchaincell.state` и снапшот, чтобы шёл полный скан).
2. Добавить **сравнительный счётчик** в верификаторе: вердикт по кэшу против
   вердикта по событиям леджера. События берутся там же, где их читает
   `s_stake_ext_event_verify` (:652) — `dap_ledger_event_get_list_ex`; `end_time`
   пересчитывается той же формулой `s_stake_ext_calc_end_time()` (:679).
3. Прогнать полный реплей и сравнить счётчики.
   - **Ноль расхождений** — правка не меняет ни одного исторического вердикта,
     её можно вводить под декретом с датой после последнего блока.
   - **Есть расхождения** — каждое разобрать поимённо: если это ожидаемое
     изменение (устаревший кэш отвергал законный разлок или пропускал
     незаконный), правило вводится декретом с границей, отсекающей спорную
     историю; если расхождение означает потерю законного разлока — правка
     отменяется, причина разбирается заново.
4. Повторить на второй цепи (не только Backbone), если разлоки на ней есть.

## 6. Границы этого документа

- Никаких правок вердикта в текущем цикле — только анализ и prerequisites.
- Кэш **остаётся** ускорителем чтения для CLI, цен и статистики; речь идёт
  исключительно о том, чтобы он перестал быть источником истины для вердикта
  валидации (оценка масштаба — E3).
- Оценка объёма работ по prerequisites и по переносу трёх чтений — отдельная
  задача после E4, требующая решения о декрете.
